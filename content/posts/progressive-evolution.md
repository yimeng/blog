# 渐进式演进：不要大爆炸重构

## 大爆炸重构的诱惑与风险

```
"旧架构太乱了，一次性停掉所有旧服务，上线新架构！"
```

**风险**：
- **切换窗口数据断流**（QoS 0 无法补回）
- **新链路有未发现的 bug**（生产事故）
- **回滚困难**（旧数据可能已丢）

**实测教训**：某次切换中，新链路的时间戳 bug 导致 8 小时偏移，如果直接停旧服务，数据就全乱了。

## 为什么大爆炸重构总是失败

### 失败原因 1：新链路一定有未发现的 bug

**任何新链路都有 bug**，只是你还没发现：
- 时间戳格式不对（本地时区被当 UTC）
- 字段映射错误（metric_name 不匹配）
- 数据类型错误（字符串被当数值）
- 并发问题（max_in_flight 导致消息损坏）

**这些 bug 只有在真实数据跑起来后才会暴露**。大爆炸重构意味着"用生产环境测新链路"，风险极高。

### 失败原因 2：切换窗口数据断流

**QoS 0 的残酷现实**：
- MQTT QoS 0 消息**不重传**
- 切换窗口（几秒到几分钟）的数据**永久丢失**
- 你以为是"秒级切换"，实际是"数据断流"

**实测**：某次切换中，Redpanda 重启导致 240 秒中断，期间 2,713 条消息 100% 丢失（QoS 0 源属性，所有消费者都丢）。

### 失败原因 3：回滚困难

**大爆炸重构的回滚成本**：
- 旧数据可能已丢（切换窗口的数据断流）
- 旧服务可能已停（需要重新部署）
- 回滚需要时间（而数据还在断流）

**回滚不是"重启旧服务"那么简单**——数据一致性已经破坏。

## 正确做法：渐进式演进

### 第 1 步：新链路先旁路运行

```
旧链路（生产，继续跑）：
  mqtt-ingest → power_metrics / device_state_metrics

新链路（旁路，不影响旧链路）：
  redpanda-connect → obs_numeric
```

**关键**：新链路先跑起来，**不影响旧链路**。这样即使新链路有 bug，旧链路数据完整。

**为什么旁路运行重要**：
- 新链路的 bug 在旁路阶段暴露（不影响生产）
- 可以对比新旧链路的数据（验证一致性）
- 回滚成本为零（旧链路一直在跑）

### 第 2 步：双写对账验证一致性

```
对账窗口：修复后纯净窗口（5 小时）

结果：
- 泵 23 指标：100% 通过，数量差 -0.01%
- 电表 37 指标：100% 通过，数量差 0.00%
- 事件：旧表真状态变化 265 条 == 新表 265 条，差 0
```

**关键**：双写对账证明新链路数据与旧链路一致，才能进入下一步。

**对账的核心价值**：
- 验证新链路数据正确性（不是"看起来对"，是"数值一致"）
- 发现新链路的语义差异（比如 obs_event 过滤了 143 条属性噪声）
- 确认新链路可以替代旧链路（数据完整、语义正确）

### 第 3 步：逐个消费者迁移

```
迁移顺序（从简单到复杂）：
  1. Grafana 加新面板查 obs_numeric（与旧面板并存）
  2. 分析服务改读新表（watcher/judge）
  3. 停旧写入服务
  4. 观察期后清理旧表
```

**关键**：**逐个迁移，每个有独立验证**。不要同时停多个服务。

**为什么逐个迁移**：
- 每个迁移都可以独立验证（Grafana 面板数据对不对）
- 出问题可以单独回滚（只回滚这一个消费者）
- 旧服务继续跑，直到新消费者验证通过

### 第 4 步：观察期后清理

```
T+7 天：清理测试表（test、_test_2s）
T+14 天：评估 slim 表（已弃用、无依赖后 DROP）
T+30 天：评估 ha_entities/ha_devices
永久：原始观测表永不删除
```

**关键**：历史数据不删除，只停写入。观察期确认无依赖后再清理。

**为什么观察期重要**：
- 确认新链路稳定（没有隐藏 bug）
- 确认没有遗漏的消费者（所有读旧表的服务都已迁移）
- 确认数据一致性（新表数据与旧表一致）

## 通用原则

**渐进式演进的核心是"可回滚"**：
- 每一步都有回滚路径（重启旧服务即恢复）
- 新链路先旁路验证，不直接替换
- 双写对账证明一致性后才切换
- 历史数据不删除，只停写入

**不要大爆炸重构**：一次性停掉所有旧服务上线新架构，风险远大于收益。渐进式演进虽然慢，但每一步都可验证、可回滚。

## 误区与边界

### 误区 1：以为"新架构已经测过了"

实际上：
- 测试环境和生产环境的数据不同（真实数据会暴露更多 bug）
- 新链路的 bug 只有在真实数据跑起来后才会暴露
- **"测过了"不等于"生产上没问题"**

### 误区 2：以为"切换窗口很短没关系"

实际上：
- QoS 0 消息不重传，切换窗口的数据永久丢失
- 你以为是"秒级切换"，实际是"数据断流"
- **短窗口也有数据损失**

### 边界：什么时候可以快一点

- 新链路已经旁路运行很久（数据已验证一致）
- 切换窗口可以选在"数据最不敏感"的时段（比如凌晨）
- 有完整的回滚预案（旧服务可以快速重启）

**但即使这样，也建议渐进式演进，不要大爆炸**。

## 原则提炼

1. **新链路一定有未发现的 bug**：旁路运行让 bug 在不影响生产的情况下暴露
2. **双写对账是切换的前提**：证明新链路数据与旧链路一致，才能进入下一步
3. **逐个消费者迁移**：每个迁移都可以独立验证、独立回滚
4. **历史数据不删除**：只停写入，观察期确认无依赖后再清理

**渐进式演进虽然慢，但每一步都可验证、可回滚。不要大爆炸重构。**
