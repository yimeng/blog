## 大爆炸重构的诱惑与风险

```
"旧架构太乱了，一次性停掉所有旧服务，上线新架构！"
```

**风险**：
- 切换窗口数据断流（QoS 0 无法补回）
- 新链路有未发现的 bug（生产事故）
- 回滚困难（旧数据可能已丢）

**实测教训**：某次切换中，新链路的时间戳 bug 导致 8 小时偏移，如果直接停旧服务，数据就全乱了。

## 正确做法：渐进式演进

### 第 1 步：新链路先旁路运行

```
旧链路（生产，继续跑）：
  mqtt-ingest → power_metrics / device_state_metrics

新链路（旁路，不影响旧链路）：
  redpanda-connect → obs_numeric
```

**关键**：新链路先跑起来，**不影响旧链路**。这样即使新链路有 bug，旧链路数据完整。

### 第 2 步：双写对账验证一致性

```
对账窗口：修复后纯净窗口（5 小时）

结果：
- 泵 23 指标：100% 通过，数量差 -0.01%
- 电表 37 指标：100% 通过，数量差 0.00%
- 事件：旧表真状态变化 265 条 == 新表 265 条，差 0
```

**关键**：双写对账证明新链路数据与旧链路一致，才能进入下一步。

### 第 3 步：逐个消费者迁移

```
迁移顺序（从简单到复杂）：
  1. Grafana 加新面板查 obs_numeric（与旧面板并存）
  2. 分析服务改读新表（watcher/judge）
  3. 停旧写入服务
  4. 观察期后清理旧表
```

**关键**：**逐个迁移，每个有独立验证**。不要同时停多个服务。

### 第 4 步：观察期后清理

```
T+7 天：清理测试表（test、_test_2s）
T+14 天：评估 slim 表（已弃用、无依赖后 DROP）
T+30 天：评估 ha_entities/ha_devices
永久：原始观测表永不删除
```

**关键**：历史数据不删除，只停写入。观察期确认无依赖后再清理。

## 通用原则

**渐进式演进的核心是"可回滚"**：
- 每一步都有回滚路径（重启旧服务即恢复）
- 新链路先旁路验证，不直接替换
- 双写对账证明一致性后才切换
- 历史数据不删除，只停写入

**不要大爆炸重构**：一次性停掉所有旧服务上线新架构，风险远大于收益。渐进式演进虽然慢，但每一步都可验证、可回滚。
