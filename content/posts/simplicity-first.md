## 归一化的常见误区

```
"我们要统一技术栈！全部用 Kafka/Flink/Trino！"
```

**问题**：为了"统一"，引入了更多组件，维护成本反而更高。

**错误做法**：
- 为了统一而引入 Kafka（消息队列）
- 为了统一而引入 Flink（流处理）
- 为了统一而引入 Trino（联邦查询）

**结果**：组件越来越多，维护越来越复杂。

## 归一化的真正目标

**归一化的目标是"减少需要维护的东西"，不是"形式上都用同一个工具"**。

| 方面 | 正确做法 | 错误做法 |
|---|---|---|
| **组件数量** | 越少越好 | 为了统一而增加 |
| **自写代码** | 越少越好 | 为了统一而重写 |
| **维护成本** | 越低越好 | 为了统一而升高 |

**归一化不是"统一技术栈"，是"减少维护负担"**。

## 实测案例：归一化的收益

**归一化前**：
- 自写服务：mqtt-ingest、homeassistant-exporter、pump-health-ingest、device-watcher、device-judge
- 代码量：2000+ 行（Python/Node）

**归一化后**：
- Redpanda Connect：5 个 YAML 配置
- HA 官方 InfluxDB 集成：1 个配置
- 自写代码：2 个小脚本（dir-sync、ha-event）
- **自写代码量减少约 85%**

**关键**：归一化减少了**需要维护的代码量**，而不是增加了组件。

## 简单优先的具体原则

### 1. 组件越少越好维护

```
错误：MQTT → Kafka → Flink → Trino → GT
正确：MQTT → Redpanda → GT
```

**每少一个组件，就少一份维护、少一个故障点**。

**为什么 Kafka/Flink/Trino 不适合家庭场景**：
- Kafka：需要维护 broker、ZooKeeper/KRaft、分区、副本
- Flink：需要维护流处理作业、状态后端、检查点
- Trino：需要维护查询集群、数据源连接、资源调度

**家庭场景的数据量**（每天几十万行）**根本不需要这些重型组件**。

### 2. 自写代码越少越好维护

```
错误：为了统一，把 Redpanda 的配置改成自写 Python
正确：能用 Redpanda 的 yaml 配置就用，特殊协议才自写薄脚本
```

**Redpanda 的 websocket input 接不了 HA 多步握手，所以用 subprocess + 60 行薄脚本，而不是重写整个采集器**。

**自写代码的成本**：
- 需要维护（bug 修复、协议变更、性能优化）
- 需要测试（单元测试、集成测试、回归测试）
- 需要文档（代码注释、使用说明、故障排查）

**Redpanda 的 yaml 配置的成本**：
- 只需要改配置（不需要写代码）
- 有官方维护（bug 修复、功能更新）
- 有现成文档（配置说明、示例）

### 3. 归一化的边界是"协议限制"

**归一化不是万能的**：
- Redpanda 的 websocket input 只支持单条 open_message
- HA 的两步握手（auth → subscribe）接不了
- **必须自写薄脚本**，这不是设计缺陷，是协议限制

**接受这个边界，不要为形式统一而引入风险**（比如 mqtt_eventstream 需要重启 HA + legacy 风险）。

**归一化的边界**：
- 标准协议（MQTT/HTTP）→ Redpanda
- 特殊协议（WebSocket 多步握手、命令式查询）→ 自写薄脚本
- **归一化的目标是"减少维护负担"，不是"形式上都用同一个工具"**

## 通用原则

**"简单"不是将就，是正确架构**：

- 组件越少越好维护
- 自写代码越少越好维护
- **归一化的目标是"减少维护负担"，不是"形式统一"**

**KISS 原则**：Keep It Simple, Stupid. 简单不是妥协，是最佳选择。

## 误区与边界

### 误区 1：以为"组件越多越好"

实际上：
- 每个组件都有维护成本（部署、监控、升级、排错）
- 组件越多，故障点越多
- **组件数量与维护成本成正比**

### 误区 2：以为"自写代码更灵活"

实际上：
- 自写代码需要维护（bug 修复、协议变更、性能优化）
- 自写代码需要测试（单元测试、集成测试、回归测试）
- 自写代码需要文档（代码注释、使用说明、故障排查）

**"灵活"的代价是"维护成本"**。

### 边界：什么时候该自写

- 标准协议无法满足（WebSocket 多步握手、命令式查询）→ 必须自写
- 官方组件有语义缺口（old_state、quality 等）→ 必须自写
- 特殊业务逻辑（设备指纹、活动识别）→ 可以自写

**但即使自写，也尽量用"薄脚本 + 成熟组件"的方式**（subprocess + Redpanda），而不是全自写。

## 原则提炼

1. **组件越少越好维护**：每少一个组件，就少一份维护、少一个故障点
2. **自写代码越少越好维护**：能用成熟组件就用，特殊协议才自写薄脚本
3. **归一化的目标是"减少维护负担"**：不是"形式上都用同一个工具"
4. **归一化的边界是"协议限制"**：接受边界，不要为形式统一而引入风险

**简单不是妥协，是最佳选择**。KISS 原则：Keep It Simple, Stupid.
