## 家庭服务的特殊性

**家庭服务与企业服务的本质区别**：
- 设备会坏、会断连、会离线（BLE 断开 8 天没人知道是常态）
- 人不会时刻盯着（没有 7×24 运维）
- 数据丢了就是丢了（QoS 0 无法挽回）
- 没有专职 SRE（你是唯一的运维）

**但这不意味着可以忽视可靠性**。

## 家庭场景需要的基本韧性

### 1. 备份（但要知道备份在哪里、能不能恢复）

```
错误做法：
- "我有备份"（restic timer 已停，但没人知道）
- "PVE 有快照"（但从未验证过能恢复）

正确做法：
- 备份 timer 停了 → 明确知道"当前无自动备份"
- PVE 快照 → 至少验证一次能完整恢复
- 关键数据（Vault、语义层）→ 有独立的备份策略
```

**原则**：**备份不是"有就行"，是要知道"在哪里、能不能恢复、恢复要多久"**。

### 2. 可观测性（掉线了能知道，而不是几天后才发现）

```
错误做法：
- 泵掉线 8 天没人知道（BLE 断开，数据静默）
- 备份 OOM 没人知道（导出大表导致内存峰值 2.2G）
- device-judge token 被吊销两周没人知道（每轮报错但没人看）

正确做法：
- 健康信号记录（health_ingest_alive 心跳）
- 数据源新鲜度检查（data-source-health.md）
- 统一告警（虽然"以后再做"，但先记录健康信号）
```

**原则**：**可观测性不是"以后再做"**，是现在就要记录健康信号，哪怕告警以后再做。

### 3. 渐进式改动（先验证再切换，不大爆炸）

```
错误做法：
- 一次性停掉所有旧服务上线新架构
- 直接改生产配置（rt=200ms → 2000ms 导致泵宕机）

正确做法：
- 新链路先旁路运行（不影响旧链路）
- 双写对账验证一致性后才切换
- 连通性变更带自动回滚（5 分钟未验证则恢复原配置）
```

**原则**：**渐进式改动，每一步都有回滚路径**。

## 家庭场景的可靠性底线

| 底线 | 说明 |
|---|---|
| **数据不丢** | QoS 0 无法挽回，但 sqlite buffer 能保住已收到的 |
| **掉线能知** | 健康信号记录，哪怕告警以后再做 |
| **可回滚** | 每一步都有回滚路径，不大爆炸 |
| **备份可恢复** | 知道备份在哪里、能不能恢复、恢复要多久 |

**家庭服务不需要企业级的复杂度，但需要基本的韧性**：
- 备份（可验证的备份）
- 可观测性（掉线能知道）
- 渐进式改动（先验证再切换）

## 通用原则

**可靠性不是可选项，是家庭数据工作的底线**：

- 设备会坏、会断连、会离线（这是常态，不是异常）
- 人不会时刻盯着（掉线 8 天没人知道是常态）
- 数据丢了就是丢了（QoS 0 无法挽回）

**家庭场景的可靠性思维**：
- 不追求企业级的复杂度
- 但要有基本的韧性（备份、可观测性、渐进式改动）
- **可靠性不是"以后再做"，是现在就要考虑**
